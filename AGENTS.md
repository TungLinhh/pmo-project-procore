# PMO — agent notes

Stack: npm workspaces (`backend`, `frontend`), ESM, Node 22+, Postgres 16 + pgvector. No TS, no test runner — tests are plain `node tests/e2e/*.mjs` (current inventory 121 files; `npm test` runs only 4).

## Commands
- `npm install` (root) → `node backend/src/db/init.js` (migrate+seed, idempotent) → `npm run dev` (backend :3000 + frontend :5173)
- `npm run build` / `npm start` — single-port prod (backend serves `frontend/dist`)
- `npm test` — 4 CI suites only: `api` + `payment-sla` + `shop-approval` + `schema`. Fuller: `npm run test:all` (+ browser + `tests/tools/schema-audit.mjs`)
- Single test: `node tests/e2e/<name>.mjs`; full pipeline on scratch DB: `node tests/e2e/pipeline-guard.mjs` (DB `pmo_pipeline` on :3244, drops itself)
- Gate nhóm: `test:security` (refresh-reuse + realtime + secrets-hygiene), `test:monitoring`, `test:retention`, `storage:gc`. Chạy tuần tự, cần `LOGIN_RATE_MAX=1000`
- Lint: `npm run lint --workspace=backend` (`node --check` loop over `src/index|lib|routes` only — `db/`, `services/` not covered) / `--workspace=frontend` (`oxlint`); frontend build: `npm run build --workspace=frontend`
- Local PG: `./backend/scripts/pg-ctl.sh start` — `127.0.0.1:5433` (`pmo_user/pmo_dev_pwd/pmo`); compose PG is `5432` inside, `5433` on host

## DB — Postgres only
- `DATABASE_URL` wins; else `DB_*`. Request pool uses `APP_DB_USER` (default `pmo_app`, escape hatch `pmo_user`); migrations/seeds use owner pool via `getOwnerDb()`. Never use owner pool in routes.
- RLS via `app.current_tenant` GUC + `AsyncLocalStorage` set in `requireAuth`. Unauthenticated paths run with no tenant (hatch). App role must stay non-superuser (superusers bypass RLS).
- `db.prepare()` uses `?` placeholders (converted to `$N`; pre-existing `$N` left alone). `getAsync()` auto-appends `LIMIT 1` unless SQL has LIMIT/RETURNING. INSERT auto-appends `RETURNING id` only if table has `id` col (probed once, cached).
- `NUMERIC` arrives as float (driver parses oid 1700). Use `db.upsert()` — requires unique index to exist; empty `setCols` = DO NOTHING.
- Migrations: `backend/drizzle/*.sql` + ledger `schema_migrations` (checksum). Drift or `//` comments in SQL = boot fails. Never edit applied file; add new file. Ordering is explicit rank list in `db/migrate.js:orderedMigrationFiles` (currently through `9999an`, rank 41). `CREATE EXTENSION vector` needs superuser.
- `node backend/src/db/init.js` also seeds tenants/users/BTE project+zones, sets `admin123` hashes, resyncs sequences. Idempotent.

## Auth / permissions / state
- JWT access (`ACCESS_TTL_SEC`, default 24h) + rotating refresh; `requireAuth` reloads user row every request. `must_change_password=1` gates everything except `/api/me/password`, `/api/auth/logout*`, `/api/me` (403 + `PASSWORD_CHANGE_REQUIRED`).
- `ceo` is `role='pmo' + is_ceo=1`, not a role value — check via `requireRole('ceo')` / `held` set.
- Canonical matrix: `backend/src/lib/permissions.js` (`own` = pm_user_id or `project_members`; `assigned` = `project_members`). Wrong project → 404, wrong role → 403. Plan gates (`tenants.plan` via `GET /api/me/entitlements`, `lib/entitlements.js:requireFeature`) → 403.
- All status changes via `lib/transitions.js:checkTransition()` (illegal → 422) + `withAudit/txAudit` (business + `audit_log` in one tx). Demo password for all e2e logins: `admin123`.

## API / frontend quirks
- Mount order in `backend/src/index.js` matters: `/api/stream` (SSE) first; `/api/me` privacy router before meRouter; `/api/projects/:id/kpi-targets` before `/api/projects`; static upload subpaths (`/review|/batch|/classify`) before greedy `/:id`; unknown `/api/*` → JSON 404 (never SPA HTML).
- Upload dual prefix is intentional: `POST /api/upload[/batch|/classify|/:id/configure|preview|commit]` (writes) + `GET /api/uploads[/review|/:id[/rows|download]]` (reads). Same routers mounted twice — do not dedupe/redirect (breaks 50MB multipart).
- Wizard flow: `configure → preview → commit` (idempotent upsert, reruns don't duplicate).
- Frontend `src/api/index.js` uses relative `/api` (Vite proxies to :3000); `qs()` strips `undefined/null/''`; `exportApi.ENABLED=false` (module-specific legacy exports stay off; project report route is separate); demo guide is `docs/DEMO_GUIDE_VI.md`; primary project `BTE-WP4-HBC`.
- Storage: content-addressed `sha256.ext` via `lib/storage.js`; `STORAGE_DRIVER=local` default. S3 path: `storage.path()` throws — use `withTempFile/readBuffer/download`. Test mocks: `AI_MOCK=1`, `S3_EMULATOR=1`.

- **`setval(seq, MAX(id))` cuộn lùi sequence và làm lịch sử kiểm toán mơ hồ** (11.27.9): `MAX(id)` nhỏ lại sau khi xoá dòng, nên `init.js` chạy lại sẽ cấp lại id mà `audit_log` (cố ý **không** có FK) vẫn trỏ tới. Đo: sequence `67 → 28`. Sửa: `GREATEST(last_value, MAX(id), MAX(audit_log.resource_id))`, bảng rỗng thì để nguyên. Nên bất kỳ script nào chạy `init.js` trên **database đang dùng** cũng phải được coi là thao tác nguy hiểm về id.
- **Bất biến "id không được cấp lại" chỉ đúng tại lúc nó được đo** — và **không** kiểm được trong `release-gate.mjs`. Mốc là `MAX(audit_log.resource_id)`, mà bài kiểm của gate tạo rồi xoá dữ liệu thử nên mốc **dịch lên trong lúc gate chạy**; đặt `scripts/check-id-reuse.mjs` vào gate là bài tự đỏ chính mình (đo: 3/66 bảng bị báo, do gate tạo ra). Chỗ đúng là `deploy/single-machine/install.sh`, chạy **trước** khi dịch vụ lên, và chạy lại sau mỗi lần dọn dữ liệu lớn. Bài đó phải dùng `getOwnerDb()`: đọc `last_value` của sequence cần quyền sở hữu, mà app role cố ý không có — dùng `getDb()` thì nó kiểm được **1/66** bảng rồi in "✓".
- **Cổng 3000 do dịch vụ systemd giữ** (11.27.7): khởi động server bằng tay mà quên dừng dịch vụ thì server tay chiếm cổng trước, dịch vụ lặp `Restart=always` với `EADDRINUSE`, mà `/api/health` vẫn 200 nên **tưởng dịch vụ đang chạy** (đo: `is-active` = `activating` vô tận, `production-readiness` 5/13 thay vì 8/13). Chạy bộ e2e thì dừng dịch vụ trước — `run-all-e2e.mjs` tự bật server riêng.
- **Bài kiểm portability phải dò cả tên người dùng, không chỉ đường dẫn**: `p2-02` trước đây chỉ dò `/home/`, `/Users/`, `C:\`, nên bỏ lọt ba bài ghi cứng `psql -h /tmp -U <tên máy tác giả>` (`p3-ledger`, `p3-sequences`, `p3-txaudit`). Nay dùng `adminPsql()` trong `tests/tools/env.mjs` (ghi đè `PGUSER_ADMIN`/`PGHOST_ADMIN`/`PGPORT_ADMIN`) và bài kiểm dò cả `scripts/`.
- **`sleep(3500)` sau khi spawn server là bẫp, không phải chờ**: 56 bài làm vậy; chạy cả bộ thì server chưa kịp lên ⇒ `TypeError: fetch failed / ConnectTimeoutError` trông y hệt lỗi sản phẩm. Dùng `waitForServer(base)` trong `tests/e2e/lib.mjs` (dò `/api/health`, liveness-only, không chạm DB). **Cẩn thận**: chỉ thay ở bài thực sự spawn server, và **không** thay sleep mang ý nghĩa khác — `p2-jwt-auth` dùng `sleep` để chờ **TTL 3 giây hết hạn**, thay bằng `waitForServer` là bài kiểm sai thứ (đã sửa thành chờ tới khi server thật sự từ chối token).
- **5xx phải qua `errorBody()`, và phải trả `e.status`**: `res.status(500).json({ error: e.message })` vừa bypass `lib/error-body.js` (ở `NODE_ENV=production` trả nguyên lỗi Postgres ra client — đo: `value too long for type character varying(100)`), vừa **nuốt mất `e.status`** mà `lib/baseline.js` / `lib/erp-fast.js` cố ý bơm vào (`Object.assign(new Error(…), { status: 404|409|422 })` ⇒ 409 "lịch đã đổi" thành 500 vô dụng). Đúng là `res.status(e.status || 500).json(errorBody(e))`; có trường phụ thì `{ ...errorBody(e), k: … }`. Bảo hiền: `scripts/check-5xx-bodies.mjs` trong gate — nó bắt theo **`.message` trong câu lệnh** chứ không theo tên biến `e`, và khớp **mọi** biểu thức trạng thái có thể ra 5xx (`res.status(500)` *lẫn* `res.status(e.status || 500)`). Bỏ sót một cách viết là bỏ sót một nửa lỗi: bản đầu chỉ khớp `res.status(500)` nên **bỏ lọt 47 chỗ**.
- **`requireRole()` không đi qua ma trận**: nó kiểm tập role rồi `next()` — không gọi `canAccess()`, nên không tính `own`/`assigned`/`project_members`. `scripts/list-unmatrixed-writes.mjs` đếm 117 route ghi không gọi `requirePermission` (28 mở cho `ceo`); ma trận chỉ phủ 16/25 module, phần còn lại (`bim`/`ai`/`erp`/`jobs`/`holidays`/`manpower-plan`) chỉ có `requireRole`. Chưa quyết, xem `DATA_DECISIONS_REQUIRED.md` mục 16.
- **Bài kiểm tự tạo database thì phải cấp quyền app role**: `GRANT` gắn theo **database**, nên role có `pmo` chưa chắc có `pmo_pipeline`/`pmo_freshtest`. Không cấp thì mọi request của server sạt trả `500 permission denied for table …` (đo: `GET /api/dashboard` → 500 trên DB sạch, trong khi gate chạy trên DB dev nên không thấy). `pipeline-guard.mjs` + `freshdb-init.mjs` đã tự `GRANT CONNECT`/`USAGE`/`SELECT,INSERT,UPDATE,DELETE`/`USAGE,SELECT ON SEQUENCES` bằng **admin** trước khi spawn server.
- **Tạo role `BYPASSRLS` cần superuser**; `psql -h /tmp -p 5433 -U vutun` là local superuser trên máy dev. Sau khi tạo, `deploy/production/00-backup-role.sh` chạy được thật (đo: dump 20 MB, 1097 TOC entry, `pg_restore -l` đọc được) và `backup.mjs` xanh.

## Đợt 20 — bài học về "đã triển khai" và về bài kiểm tự báo sai
- **`is-active` không phải bằng chứng sản phẩm đang phục vụ.** `pmo-api.service` báo `active` trong khi `/api/ready` trả 503 vì Postgres đã chết. Đo bằng `/api/ready`, không bằng `is-active` — và `/api/health` cũng vô dụng ở đây vì nó **cố ý** không chạm DB. Sự "sống" phải đo bằng thứ *mà người dùng gặp*, tức truy vấn thật.
- **Bản "đã triển khai" phải trả lời: sau khi nó chết, ai bật lại?** Không gì tự bật Postgres (data dir nằm trong repo, không thuộc `postgresql.service` hệ thống) ⇒ sau reboot là mất demo. Nay `pmo-db.service` + `pmo-api.service` khai `Requires=`/`After=`, và `pmo-watchdog --heal` tự phục hồi. **Đo bằng cách giết thật**: `kill -9 $(head -1 data/pgdata/postmaster.pid)` rồi bốn lần `curl /api/ready` mỗi 15s — đo 2026-09-30: gián đoạn 14s, tự lên, không cần người.
- **Lệnh khôi phục phải chạy được thật, không chỉ được viết.** `pg-ctl.sh start` in *"PG already running"* vì kiểm `[ -f postmaster.pid ]` thay vì hỏi cổng ⇒ no-op **báo thành công**. Loại lỗi nguy hiểm nhất: không hỏng, chỉ nói dối. Mẫu chung: mọi lệnh khôi phục phải **tự xác nhận bằng cách đo** (`pg_isready` sau `pg_ctl start`), và lỗi phải **liệt kê chỗ đã thử** thay vì một dòng chung chung.
- **Chạy được trong shell ≠ chạy được dưới systemd.** `pg-ctl.sh` tìm `pg_ctl` qua `PATH`; user unit có `PATH=/usr/local/bin:/usr/bin:/bin` nên không có Homebrew. Bài kiểm gõ tay trong shell vẫn xanh. Script chạy dưới systemd phải có danh sách đường dẫn dự phòng.
- **Một sự vật, một chủ.** Watchdog gọi `pg-ctl.sh start` trực tiếp ⇒ dựng Postgres mà systemd không biết; systemd sau đó hạ `pmo-db.service` thì `ExecStop` giết **đúng instance vừa dựng** (đo: hồi lại 20:40:43, "smart shutdown" 20:40:44 — một giây sau khi khoẻ, không ai hiểu vì sao). Phục hồi phải **qua systemd**, không gọi lệnh ngoài.
- **`TimeoutStartSec` phải tính từ thời gian thật, không từ cảm giác.** probe 13s + dựng PG 25s + probe lại 13s = 51s; đặt 60s thì systemd giết watchdog **giữa lúc đang dựng DB**, rồi hạn mức 5 phút làm mất cả cửa sổ hồi phục kế tiếp. Số "nhanh" của từng bước không dựng ra tổng.
- **Bắt `stderr`, đừng cắt thông báo lỗi.** `execFileSync(..., { stdio: 'ignore' })` ⇒ `e.stderr` rỗng ⇒ chỉ còn `"Command failed"`, mất 20 phút chẩn đoán. Và cắt bớt cũng là giấu lỗi: `slice(0, 120)` trong khi thông báo tự nó đã vô dụng.
- **Gộp argv là lỗi riêng, nhỏ mà tốn thời gian.** `systemctl --user restart 'a.service b.service'` ⇒ `Invalid unit name "a.service b.service" escaped as "a.service\x20b.service"`. Phải truyền từng phần tử.
- **"Có mặt ở đâu đó trong hàm" KHÔNG phải bằng chứng hành vi.** Đợt 20 có **ba** khẳng định tự báo sai, đều do phép thử âm tính bắt chứ không phải do đọc code: (1) lát cắt tới hàm nằm **trước** ⇒ lát cắt rỗng ⇒ luôn xanh; (2) lát cắt **rộng quá** ⇒ bắt nhầm hàm khác ⇒ đỏ oan; (3) so `pmo-db.service` "ở đâu đó trong hàm" thì **thông báo trả về** làm xanh dù lệnh đã bị xoá. Sửa: soi **đối số của lời gọi hàm**. Cùng bài học cũ: quét cả **comment** và **chuỗi thông báo** — comment giải thích trong chính hàm có thể chứa đúng mẫu đang đo.
- **Kiểm tên hằng là kiểm không đủ.** `ok(/COOLDOWN_MS/.test(w))` xanh cả khi đặt `= 0`. Phải kiểm **giá trị**; mà `([\d_]+)` trên `5 * 60_000` ra `5` ⇒ phải **tính** biểu thức, không bắt chữ số đầu.
- **Số tiến trình: đừng dùng `pgrep -f` với mẫu nằm trong chính dòng lệnh.** `pgrep -f "data/pgdata"` khớp luôn shell đang chạy lệnh, nên `kill -9` giết chính shell. Lấy pid từ **pid file** hoặc dùng mẫu không khớp dòng lệnh.
- **Bài kiểm cho script vận hành phải chạy trên data dir giả.** `PG_DATA="${PG_DATA:-…}"` cho phép `pg-ctl.sh` được kiểm trong `tmpdir` với `pg_isready`/`pg_ctl` giả, thay vì đụng dữ liệu thật. Nhớ **phép thử dương** bên cạnh phép thử âm tính: chỉ chứng minh "có gọi `pg_ctl`" chứ không chứng minh nó gọi **đúng lúc** — phải có lần gọi thứ hai và khẳng định lần đó **không** gọi.

## Đợt 21 — dời dữ liệu, và "sửa một" khi cần sửa hai
- **Đừng tin rằng một thay đổi đã đủ; hãy đo lại *tín hiệu người dùng thấy*.** Dời lịch demo 2019 → 2026 được kỳ vọng làm nén lịch chạy được. Đo thì `calendar_end` **y hệt** trước và sau (2027-06-25), vì `lib/cpm.js:mapToCalendar` dàn hạng mục chưa làm ra từ `todayStr()` — nó phụ thuộc **hôm nay**, không phụ thuộc ngày lưu trong DB. Đây là **hai vấn đề tách biệt**; sửa một và khen là "giao diện đẹp hơn" là báo xong sai. Trước khi kết luận, đo lại **con số người dùng nhìn thấy**, không chỉ việc đã sửa.
- **Khi dời dữ liệu, tính phạm vi từ schema chứ đừng đoán.** Bản đầu liệt kê 4 bảng gắn `project_id`; `information_schema` cho ra **19 bảng gắn dự án + 4 bảng nối gián tiếp**. Dời lịch mà không dời payment/contract thì demo **tự mâu thuẫn**. Trước khi sửa dữ liệu hàng loạt: liệt kê cột ngày theo `information_schema`, rồi ghi rõ bảng nào nối qua khoá nào.
- **Chỉ dời ô thật sự cần dời — theo từng cột, không theo cả dòng.** Đo được hai thứ đang ở **hiện tại** giữa chừng dữ liệu 2019: `attention_digest_runs.digest_date` = 2026-09-26→29 (lịch sử cron; dời ⇒ 2033 ⇒ cron tưởng hôm nay chưa chạy ⇒ gửi trùng) và `projects.end_date` = 2027-01-20. Dùng `CASE WHEN col < mốc THEN col + offset ELSE col END` cho **từng cột**. Dùng `AND` giữa các cột nghĩa là "mọi cột đều cũ" ⇒ dòng có một cột hiện tại sẽ bị bỏ qua hẳn, tức sót dữ liệu 2019 trong chính dòng đó. Cách này tự loại mọi trường hợp tương tự mà không cần danh sách cấm thủ công.
- **Cột thời gian hệ thống (`created_at`, `updated_at`, `sent_at`) không dời.** Chúng là dấu vết thao tác, không phải ngày nghiệp vụ; dời chúng làm nhật ký kiểm toán sai.
- **Offset dịch dữ liệu phải ghim, không tính lại mỗi lần chạy.** `init.js` chạy mỗi lần khởi động; tính offset mỗi lần thì ngày trôi mãi và mọi báo cáo đã chép ra sẽ sai. Ghim vào bảng singleton, và kiểm tra ghim phải **đứng trước** lượt quét — nếu không, lần chạy sau sẽ in "không làm gì" thay vì "đã ghim", tức thông báo sai lý do.
- **Đoán một ngày "khả thi" là sai khi kết quả phụ thuộc tham số.** `calendar_end + 1` cho 2027-06-26, dùng vào lại **không** khả thi: mục tiêu xa hơn ⇒ nén ít hơn ⇒ lịch dài hơn (2027-06-25 → 2027-07-01). Bài toán điểm cố định thì phải **tìm** (quét bước rồi nhị phân), và hàm tính phải **thuần** để tìm không tốn truy vấn. Kèm theo: dữ liệu phụ thuộc tham số (ngày nghỉ) phải nạp theo **chân trời tìm kiếm**, không theo giá trị đầu vào.
- **Thêm bảng mới làm hỏng `pg_dump` nếu role sao lưu chưa có quyền.** `ALTER DEFAULT PRIVILEGES` chỉ phủ object tạo **sau** nó **bởi đúng role đã đặt**; migration chạy bằng `pmo_user` còn `00-backup-role.sh` thường chạy bằng `vutun`. Đo 2026-09-30: thêm bảng ⇒ `POST /api/admin/backups/run` trả 500. Sửa: `init.js` cấp lại `GRANT SELECT` cho `pmo_backup` sau **mỗi** lần migrate, có điều kiện role tồn tại. Và bài kiểm sao lưu phải kiểm **quyền** chứ không chỉ "dump chạy được" — bảng mới rỗng thì `pg_dump` không đọc tới, nên kiểm cũ vẫn xanh.
- **Thứ tự đánh giá điều kiện trong Postgres không được bảo đảm.** Gọi hàm có thể ném lỗi trong `WHERE` của một join là không an toàn: hàm có thể chạy trên dòng mà điều kiện kia sẽ loại (đo: `has_sequence_privilege` ném `pg_toast_24682 is not a sequence`). Subquery trong `FROM` **không** đủ vì Postgres **rút phẳng** (subquery pull-up) subquery đơn giản; chỉ `WITH … AS MATERIALIZED` mới chặn được. Và overload 3 tham số phải đúng thứ tự: `has_*_privilege(user, object, privilege)`.
- **Một bài kiểm chỉ bắt đầu có tác dụng khi nó được commit.** `secrets-hygiene` quét `git ls-files`; trước khi commit, chính nó và tài liệu của nó chứa tiền tố khoá **không bị thấy**. Sau khi commit thì đỏ — và nghịch lý là **không sửa thì không bao giờ commit được**, mà nằm ngoài repo thì không kiểm được gì trong CI. Giải pháp: phân biệt **khoá thật** (tiền tố + ≥32 ký tự khoá vật liệu) với **mẫu phát hiện** (tiền tố + `…`).
- **Cột ngày trả `Date` ở giờ địa phương nửa đêm; `toISOString()` ép UTC nên lệch một ngày ở múi giờ dương.** Trong công cụ dịch ngày, sai đúng một ngày là loại lỗi không ai nhìn thấy cho tới khi dữ liệu lệch. Format từ thành phần **local**, và tính phép trừ ngày bằng chuỗi `YYYY-MM-DD` so sánh chuỗi (đúng thứ tự thời gian) thay vì `Date.parse`.
- **`ok`/`ng` trong `tests/e2e/backup.mjs` là hàm GHI LOG `(name, detail)`, không phải khẳng định.** Gọi `ok(!cond, …)` ⇒ luôn in PASS. Kiểm tra chữ ký helper **trước khi** dùng, và luôn có phép thử âm tính. (Lần thứ tư gặp kiểm không thể thất bại trong hai đợt; lần nào cũng do âm tính bắt, không phải do đọc code.)
- **Đừng truyền SQL qua `bash -c` + `JSON.stringify`.** Newline thành chữ `\n`, `psql` không hiểu ⇒ `syntax error at or near "\"`. `execFileSync('psql', [args…, '-c', sql])` với **mảng tham số** không có lớp trích dẫn nào để sai.
